# HTML/JS Runtime — Design (Phase C part 2)

**Date:** 2026-07-06
**Status:** DRAFT — depends on External API v1 (Phase B) shipping; proto freeze gate pending Codex review.
**Grounded against:** `fable-design-sprint` at `be7b6b5`; spike verdict `2026-07-05-webengine-spike-results.md` (GO on all six thresholds); rails `2026-07-05-extensibility-architecture-design.md` §5 (locked: web widgets are WebSocket API clients; QWebChannel rejected; `prodigy` object is a bootstrap shim only) and §6 (WebWidgetHost enters as a normal `WidgetDescriptor`).
**Audience:** future implementing agents. The Phase C implementation plan is written against this doc (not yet authored — see §9).

## 1. Purpose

Fix the design of the web-widget runtime: how HTML/JS content is served and sandboxed, how `WebWidgetHost.qml` slots into the existing widget grid, what the injected `prodigy` object is, and how web widgets are packaged and discovered. Everything here rides on two locked facts: WebEngine is affordable on the Pi (spike: 229 MB first view, +15 MB per additional same-origin view, crash recovery proven), and web widgets talk to the head unit exclusively through the External API over `ws://127.0.0.1` (rail R3 — no second RPC surface).

## 2. Decisions (summary)

| # | Decision | Rationale anchor |
|---|---|---|
| D1 | Content served via a custom **`prodigy://` scheme** (QWebEngineUrlSchemeHandler), not file:// and not a local HTTP server | §3 |
| D2 | **One shared origin** for all widgets in v1 (`prodigy://widgets/...`) | §3 — spike finding 1 (same-origin views share a renderer, +15 MB/view) |
| D3 | Widget package = directory under `~/.openauto/webwidgets/<id>/` with a `widget.yaml` manifest; scanner maps it to a standard `WidgetDescriptor` | §4 |
| D4 | `WebWidgetHost.qml` instantiates its WebEngineView **lazily on first page visibility**, keeps it alive afterwards | §5 — spike findings 2/4 (800 ms first load; +15 MB steady-state is cheap) |
| D5 | Crash recovery = `onRenderProcessTerminated` → debounced reload, 3 attempts with backoff, then an error card with tap-to-retry | §5 — spike finding 3 (proven under SIGKILL, ~4 s recovery) |
| D6 | `prodigy` shim = two user scripts: a host-templated **bootstrap** (context + apiUrl + inline theme-token snapshot) plus a static **prodigy.js** (WS client, CSS custom properties, convenience API) | §6 |
| D7 | Protobuf in JS via **protobufjs static module**, regenerated by script when protos change (Node needed only then, never in the normal build) | §6.3 |
| D8 | v1 ships **widgets only**; fullscreen web *apps* and web *overlays* reuse the same host/shim with `prodigy.context.kind` — deferred, structure already accommodates them | §8 |

## 3. Content origin & serving — `prodigy://` scheme

A `QWebEngineUrlSchemeHandler` serves widget files from their package directories. URL shape: `prodigy://widgets/<widget-id>/<path>`, entry point `prodigy://widgets/<widget-id>/index.html` (entry file name comes from the manifest).

Why not the alternatives:
- **file://** — Chromium's file-origin semantics are hostile (opaque/per-file origins, `LocalContentCanAccessFileUrls` knobs), origin sharing is unreliable, and ws:// from file:// contexts hits mixed-content edge cases. Fragile foundation.
- **Local HTTP server** — another listening port to manage/firewall, plus either a QtHttpServer dependency or hand-rolled HTTP. The scheme handler is in-process, serves only what the handler chooses, and exposes nothing to the network.

Scheme registration and behavior:
- `QWebEngineUrlScheme::registerScheme("prodigy")` with flags `SecureScheme | LocalAccessAllowed` — **must run before `QApplication` is constructed** (Chromium requirement; this goes at the top of `main()`).
- `SecureScheme` makes the origin potentially-trustworthy, and `ws://127.0.0.1` is itself potentially-trustworthy, so the shim's WebSocket connects without mixed-content blocks.
- The handler resolves `widgets/<id>/<path>` against the scanned package root for `<id>`, with a canonical-path check (`QFileInfo::canonicalFilePath()` must stay inside the package dir) — no traversal, no symlink escape. Unknown id or path → `request->fail(QWebEngineUrlRequestJob::UrlNotFound)`.
- Content types by extension (html/js/css/svg/png/jpg/woff2/json); default `application/octet-stream`.

**Single origin (D2):** all widgets share the `prodigy://widgets` origin, so all views share one renderer process — the spike's measured cheap case. Consequence, accepted for v1: widgets share localStorage and could read each other's DOM-visible state if they embedded each other (they can't — see navigation policy §5). Web widgets are user-installed local content with the same trust level as native QML widgets (which already have full QML runtime access), so isolation between them buys little today. Per-widget origins (`prodigy://<id>`) are the recorded v2 hardening path if third-party widget distribution ever materializes; the spike says even hostile per-origin isolation (~60–100 MB/origin) stays in budget.

## 4. Packaging & discovery

```
~/.openauto/webwidgets/
  speedo/
    widget.yaml
    index.html
    speedo.js, style.css, assets/...
```

`widget.yaml` (v1 fields — mirrors `WidgetDescriptor`, `src/core/widget/WidgetTypes.hpp:29-50`):

```yaml
id: com.example.speedo        # required, unique, becomes the URL segment
name: "Speedometer"           # required — picker display name
entry: index.html             # default index.html
category: status              # picker category id (status/media/navigation/launcher)
description: "GPS speedometer"
icon: ""                # Material codepoint, same convention as native widgets
size:                          # all optional — defaults match WidgetDescriptor defaults
  minCols: 1
  minRows: 1
  maxCols: 6
  maxRows: 4
  defaultCols: 2
  defaultRows: 2
config: []                    # v1: no per-widget config schema for web widgets (v1.1)
```

A `WebWidgetScanner` (C++, runs at startup after `WidgetRegistry` exists) reads each subdirectory's manifest and registers:

```cpp
WidgetDescriptor d;
d.id = manifest.id;                       // e.g. "com.example.speedo"
d.displayName = manifest.name;
d.iconName = manifest.icon;  d.category = manifest.category;
d.qmlComponent = QUrl("qrc:/OpenAutoProdigy/qml/widgets/WebWidgetHost.qml");
d.contributionKind = DashboardContributionKind::WebWidget;   // new enum value
d.defaultConfig = { {"url", "prodigy://widgets/" + manifest.id + "/" + manifest.entry} };
// size fields copied through
```

`DashboardContributionKind` gains `WebWidget` (additive; `WidgetTypes.hpp:24-27`). Bad manifests are logged and skipped — a broken widget package must never take the launcher down. Scan-once at startup in v1; hot-reload/install UX is a wishlist item, not this design.

## 5. `WebWidgetHost.qml` — lifecycle, recovery, lockdown

One host component (`qml/widgets/WebWidgetHost.qml`), config-driven, following the existing widget contract (`property QtObject widgetContext`, pattern: `qml/widgets/BatteryWidget.qml:8`, instantiated by the grid via Loader + `WidgetContextFactory.createContext` — `qml/applications/home/HomeMenu.qml:424,575-596`).

- **Lazy instantiation (D4):** the WebEngineView sits behind an inner `Loader` that activates on the first `widgetContext.isCurrentPage == true` and stays active afterwards (`property bool everVisible` latch). Spike: ~800 ms first load argues against pre-warming all pages; +15 MB per steady view argues against tearing down on page switch (reload churn would cost more UX than the memory saves).
- **Crash recovery (D5):**

```qml
onRenderProcessTerminated: (status, code) => {
    if (retryCount >= 3) { errorCard.visible = true; return }
    retryCount += 1
    reloadTimer.interval = 1000 * Math.pow(2, retryCount)   // 2s/4s/8s
    reloadTimer.start()                                      // fires webView.reload()
}
// successful loadingChanged(LoadSucceededStatus) resets retryCount = 0
```
  Error card = themed rectangle with the widget name and "tap to retry" (resets retryCount, reloads). The compositor and other widgets are unaffected (spike T6).
- **Settings lockdown:** `javaScriptCanOpenWindows: false`, `localContentCanAccessFileUrls: false`, `localContentCanAccessRemoteUrls: true` (widgets may fetch https resources — weather APIs etc. via the phone's connectivity), fullscreen requests denied.
- **Navigation policy:** `onNavigationRequested`: accept only same-origin (`prodigy://widgets/`) top-level navigations; everything else `request.reject()`. Subresource loads are unaffected. No new windows, no external browser handoff in a car.
- **Input:** DOM touch events work as normal inside the view (spike T4 measured input latency PASS). The 3-finger gesture and EVIOCGRAB behavior live below Qt at the evdev layer and are unaffected; no special handling in the host.
- **Transparency:** `backgroundColor: "transparent"` so widget HTML with transparent body composites over the glass card like native widgets.

## 6. The `prodigy` shim

Two `WebEngineScript`s injected by the host at `WebEngineScript.DocumentCreation`, `MainWorld`:

1. **Bootstrap (templated per instance, built in QML from `widgetContext`):**

```js
window.__prodigyBootstrap = {
  apiUrl: "ws://127.0.0.1:9811",            // from api.ws_port config via host
  context: { instanceId, widgetId, colSpan, rowSpan, kind: "widget" },
  themeTokens: { "primary": "#RRGGBB", ...} // full current palette, templated inline
};
```
   The inline token snapshot exists so **first paint is already themed** — no flash while the WebSocket connects. The host regenerates spans in `prodigy.context` on span change via `runJavaScript` (a `prodigy` `contextchange` event).

2. **`prodigy.js` (static, one file, served from qrc — same bytes for every widget):**
   - Reads `__prodigyBootstrap`, applies `themeTokens` as CSS custom properties on `document.documentElement`: token `on-primary` → `--prodigy-on-primary`. Pure-CSS widgets are now fully themed with zero widget JS (rail: arch §5).
   - Opens the WebSocket to `apiUrl`, performs `ClientHello{client_kind: CLIENT_KIND_WEB_WIDGET, client_name: context.widgetId}` (localhost-trusted — no token plumbing, by design), subscribes to `system`, and live-updates the CSS custom properties on every `SystemStatus` (day/night flips propagate to all widgets in one frame).
   - Public surface (the whole of it — anything more belongs in the public API, rail R3):

```js
prodigy.ready            // Promise resolved after ServerHello
prodigy.context          // {instanceId, widgetId, colSpan, rowSpan, kind}
prodigy.apiUrl           // for widgets that want their own raw socket
prodigy.subscribe(topic, cb)   // "media"|"navigation"|"projection"|"phone"|"system"
                               // cb(statusObject); returns unsubscribe function
prodigy.dispatch(actionId, payload)        // -> Promise<bool dispatched>
prodigy.notify(message, {priority, ttlMs}) // -> Promise<notificationId>
prodigy.request(apiMessageObject)          // low-level escape hatch -> Promise<response>
prodigy.on("themechange"|"contextchange", cb)
```
   - Reconnect with capped exponential backoff (1s → 30s) and automatic re-subscribe; `prodigy.subscribe` callbacks simply resume — widget authors never handle reconnection.

### 6.3 Protobuf in JS (D7)

`prodigy.js` bundles a **protobufjs static module** generated from `proto/api/*.proto` (`pbjs -t static-module -w closure`), giving dependency-free runtime encode/decode of `ApiMessage`. Regeneration is `tools/gen-proto-js.sh` (runs `npx pbjs`; requires Node, which is needed **only when the proto changes** — never in the CMake build). The generated module is committed beside `prodigy.js`; the additive-only proto policy makes regeneration rare and old generated code forward-compatible (unknown fields are preserved/skipped by protobuf rules). Rejected alternatives: hand-rolled varint codec (maintenance trap as the schema grows); JSON transcoding on the server (second wire format — violates one-protocol; and the API's binary framing is already committed).

### 6.4 Developer story

The same widget directory runs in a desktop browser: serve it with any static server, load `prodigy.js` manually, point `apiUrl` at a paired LAN head unit (`api.expose_lan: true` + PIN pairing — remote clients authenticate, so the dev build of the shim accepts a `client_id`/secret pair via `localStorage`). This is the arch §5 promise (develop on the PC, deploy to the car) and it falls out of D6/D7 with no extra machinery beyond the dev-auth branch in `prodigy.js`.

## 7. Security model (v1)

- Renderer sandbox: Chromium defaults, untouched.
- Filesystem: widgets read only their own package dir through the scheme handler (canonical-path check); no file:// access.
- API power: a web widget has exactly the localhost-trusted API surface — same as any local process, including action dispatch. This is the arch §3.2 known simplification (no per-capability ACLs in v1); installing a web widget is trusting it like a plugin. Recorded, not accidental.
- No Qt/QML access of any kind from web content: no QWebChannel (rejected, arch §5), no context properties, nothing in `window` beyond `prodigy` + bootstrap.
- Remote subresources allowed (https), remote top-level navigation blocked (§5).

## 9. Executor guidance

- **Ordering:** implement after External API v1 (the shim is an API client; there is nothing to test it against until then). The C2 implementation plan should be authored fresh against this doc + the API plan's delivered state.
- **`QWebEngineUrlScheme::registerScheme` MUST precede `QApplication` construction** — first lines of `main()`, before the existing plugin/service setup. Getting this wrong fails at runtime with a console warning, not a build error.
- C++ pieces (`WebWidgetScheme` handler, `WebWidgetScanner`) need `find_package(Qt6 OPTIONAL_COMPONENTS WebEngineCore)` + `HAS_WEBENGINE` guard, mirroring the `HAS_BLUETOOTH` pattern (`src/CMakeLists.txt:473-490`) — dev boxes without qt6-webengine-dev must still build. Pi runtime needs `qml6-module-qtwebengine` (already installed by the spike; add to `install.sh`).
- The QML host cannot be exercised under `QT_QPA_PLATFORM=offscreen` ctest — WebEngine wants a real GL context. Test strategy: unit-test the scheme handler (path traversal, content types, unknown id) and the scanner (manifest parsing, bad-manifest skip) headless; the host itself gets a manual Pi checklist (load, crash-kill `pkill -f QtWebEngineProcess` → auto-reload, day/night flip propagates, span change fires contextchange).
- Spike gotchas carry over: `pkill -x qml6` (never `-f` in ssh one-liners), Wayland env vars for any Pi-side harness (`XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-0 QT_QPA_PLATFORM=wayland`).
- Theme token names in CSS custom properties must exactly match the API's `SystemStatus.theme_tokens` keys (hyphenated) — one vocabulary end to end; do not invent camelCase variants in the shim.
